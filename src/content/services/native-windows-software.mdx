## The capability I can prove

My public evidence for native Windows work is [SoctuKit](/work/soctukit/), a built Windows product.
Its known implementation includes C#, .NET 8, WinUI 3, Windows App SDK, XAML, MVVM,
Microsoft.Extensions.Hosting, xUnit, FluentAssertions, Inno Setup, and Windows Credential Manager
for local token storage.

That is the boundary of the claim. I do not attach invented adoption, customer numbers, or
commercial results to the project, and its public release repository does not contain the source
code.

## What native can be good at

A native Windows application can make sense when a tool needs to feel at home on the desktop, work
closely with local operating-system facilities, store credentials through Windows rather than
exposing them in a file, or provide a focused installed experience without living in a browser tab.

The right choice still depends on the job. I do not recommend native technology only because it is
interesting. We should compare distribution, update needs, integrations, offline behavior, security,
and the people who will use the tool.

## Product work around the code

The visible window is only one part of desktop software. A useful release also needs clear
application state, keyboard behavior, error feedback, safe local storage, installation, tests around
important logic, and a way to understand whether an operation actually succeeded.

For a native Windows enquiry, include the Windows versions in scope, whether the tool must work
offline, what it connects to, what it stores locally, how it should be installed, and who will
maintain or update it.
