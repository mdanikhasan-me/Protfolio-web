## A finished native Windows product

SoctuKit is my clearest public proof for native Windows and custom software work. It was built and
publicly presented as an installed Windows product rather than a browser interface or an unfinished
code sample.

The known implementation uses C#, .NET 8, WinUI 3, Windows App SDK, XAML, MVVM, and
Microsoft.Extensions.Hosting. Tests use xUnit and FluentAssertions. Distribution uses Inno Setup,
and local token storage uses Windows Credential Manager.

## Why the surrounding product work matters

Desktop software is more than the code behind a window. Installation, local state, credentials,
interface feedback, and testable behavior all affect whether the software feels dependable.

Windows Credential Manager is a concrete example. A local token should not be treated as ordinary
copy in a configuration file. Using the operating system's credential facility creates a clearer
security boundary for the installed application.

An installer is another part of the product. It turns a development build into something that can be
placed on a machine through an intentional release path.

## Architecture choices visible in public

MVVM separates presentation concerns from application behavior. XAML defines the native interface,
while hosting infrastructure provides a structured place for services and application lifetime work.
Tests around important behavior provide a repeatable signal while the product changes.

This case study stays within publicly known facts. The release repository is public, but it does not
contain the source code. I do not infer adoption, customer numbers, or commercial success from the
existence of a release.

## What SoctuKit proves

SoctuKit proves that I have taken a native Windows product through interface implementation, local
credential storage, testing, and installation. It supports a specific claim about Windows software;
it is not evidence for every desktop platform or every possible integration.
